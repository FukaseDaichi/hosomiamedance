# 譜面改善スキル「chart-feel」設計書

2026-08-15(同日改訂: 検査中心 → 生成ロジック中心に組み直し)

## 目的

譜面を**爽快で気持ち良い**ものにする。そのために、既存の言語化された譜面理論
(osu! mapping wiki 等)から「どう配置すると気持ち良いか」の配置ルールを蒸留し、
`scripts/bake-chart.py` の生成ロジックに流し込む。あわせて改善ループを回すための
プロジェクト専用スキル chart-feel を作る。

- 対象はこのリポジトリの譜面のみ。汎用スキルにはしない
- 自分の体感には頼らず、既存理論の配置ルールに当てはめる
- **理論の主な適用先は検査ではなく生成**。爽快感はノーツの選び方(連続性)と
  レーンの流れ(交互・階段)から生まれるので、`select_times` と `assign_lanes` を
  理論に沿って書き換える
- 自動検査は「改善の判定基準」ではなく「デグレ防止の安全網」。検査は生成の意図
  どおりかしか見ておらず、意図が曲に合っているか・気持ち良いかは測れない(自己参照)
- **生成ロジックを変えたときのプレイ確認は必須**。良くなったかどうかは遊ばないと
  分からない

## 改訂の経緯

初版は「理論 → 検査 → 検査を通す改善ループ」の構成だったが、アドバーサリアル
レビューと検討の結果、検査は「壊れていないこと」しか保証できず、爽快感を左右する
生成側の思想(音の種類でレーンを固定、強い音の上位N個を点在させる)が手つかずに
なることが判明。理論を生成側に流し込む構成に組み直した。

## 調査

- 主軸は osu! mapping wiki。必要なら 4 キー系(osu!mania 4K / DDR)の譜面理論を
  1 ソースだけ追加
- 蒸留の焦点は「何を検査するか」ではなく**「どう配置すると気持ち良いか」**
- このゲームに存在しない概念(ロングノーツ、スライダー、SV、キー音)は捨てる

## theory.md

各原則は「定義 / このゲームでの意味 / 生成・検査への落とし込み」で書く。初期候補:

| 原則 | 一言で | 落とし込み先 |
| --- | --- | --- |
| 音付け | ノーツは実際に鳴っている音に対応する | 検査(オンセット整合率) |
| 密度カーブ | 曲の盛り上がりと密度が一致する | 検査(セクション別密度) |
| 連続性(ストリーム) | 盛り上がりでは音符を連続させ、指の流れを作る | **生成**(select_times) |
| 交互と階段 | 近接ノーツは隣レーンへ流すか交互に打たせる | **生成**(assign_lanes) |
| 縦連の抑制 | 同レーン近接は原則禁止 | 生成+検査(GAP_LANE、既存) |
| 反復の制御 | 同じ往復(トリル)を長く続けない | **生成**(assign_lanes) |
| 強拍優先 | 低難易度ほど拍頭にノーツを置く | 検査(拍頭率の単調性) |
| 休符設計 | 高密度の後に休みを置く | 定性診断(当面) |

## 生成ロジックの書き換え

### select_times: 点在 → 連続性

現行は「強い音の上位N個」で音符が点在する。連続性ボーナス(隣のグリッド点が
選択済みなら加点)つきの貪欲選択に変え、盛り上がり区間でストリームが形成される
ようにする。BPM・拍位相・quota 配分・間隔制約は変えない。

### assign_lanes: 音の種類優先 → 手の動き優先

現行はキック=↓、スネア=↑と音の種類でレーンを固定し、衝突時は「最も長く空いた
レーン」へ逃げる(手から見ると事実上ランダム)。候補レーンをスコアリングする方式に
変える:

- 縦連の回避と同一レーン最小間隔(絶対条件)は維持
- 速い流れ(16分〜8分)では隣のレーンに加点(階段)、それ以外でも交互に加点
- 同じ往復(トリル)が続いたら減点
- 音の種類(キック=↓、スネア=↑)は加点どまりに格下げ

## 安全網検査

初版の検査3つは役割を「安全網」に変えて維持する:

1. セクション別密度が `SECTIONS` の配分と整合(±30% か 3個の大きい方)
2. オンセット整合率(bake 時のみ。mp3 解析が必要なため)
3. 拍頭率の難易度順の単調性(easy ≥ normal ≥ hard)

あわせて書き込み順序を直す。現行の `main()` は charts.json を書いてから検査するため、
検査に落ちた bake が最後に合格した譜面を壊す。検査に合格した場合だけ書き出す。

## SKILL.md の手順

1. `--verify` で現状診断 + charts.json を theory.md の原則で定性診断
2. 直すべき点を bake-chart.py の変更に翻訳(つまみ: SECTIONS 倍率、DIFFS、
   CONT_BONUS、assign_lanes のスコア重み、classify の重み)
3. 再 bake → 安全網検査。落ちたら 2 に戻る。閾値を緩めて通すのは禁止
4. パスしたら変更前後の差分(ノーツ数、レーン分布、連続性の変化)を報告
5. **プレイ確認(必須)**: `npm run dev` を案内し、変えた区間を名指しして
   確認点を具体的に伝える。ユーザーの体感が改善の最終判定
